# Emergency mode

Emergency mode is the last resort when the cluster has lost quorum for good: enough managers are gone, with their data, that a normal membership change can never be agreed again because that itself needs the missing majority. `clouduler emergency` makes one surviving manager the cluster's only voter, brings back the stacks you name (or every stack with `x-clouduler.priority: -1`), and holds every other stack off until a second manager returns.

It bypasses consensus by rewriting the node's own database. Read [Dangers](#dangers) before running it.

:::danger Not for ordinary outages
If the lost managers will come back with their data intact, do not use it: a returning manager would conflict with the one you made sole voter. If a majority of managers is still up, do not use it either; use [`clouduler node remove`](/docs/features/node-lifecycle#remove-a-node) for the dead ones.
:::

## When to use it

- A blackout or dead disks took out most managers and their raft state is gone with no usable backup.
- A multi-site partition left one site with a minority of managers and the other site is not coming back.
- You need one important stack (say, your DNS or password manager) running again right now.

## What it does

1. Reads the stacks' specs from this node's own local state and works out which volumes they mount. With no stack named it takes every stack with `x-clouduler.priority: -1`, and refuses if there is none. A stack not in the local state (deployed after this node last replicated) is refused.
2. Asks for confirmation (one line).
3. Rewrites the local raft membership so this node is the **only voter**. The other nodes stay known as learners, not dropped, so they can rejoin.
4. Records the stacks as the **emergency stacks**.
5. Marks every other node unreachable, so served drives the stacks use fail over to this node.
6. Marks each volume the stacks use as current on this node: this node becomes the primary. Nothing is pulled from elsewhere.
7. Writes the state back. Assignments and every stack's desired state are not changed.

Then it starts the daemon again. Only the emergency stacks are scheduled.

## Run it

There is no web UI for this. It runs on the node you are rescuing and restarts that node's daemon through systemd (`clouduler.service`); you do not stop it yourself. It then **blocks** until every instance of the emergency stacks runs, printing a line whenever one changes, with the reason when it is held back (for example `docker daemon unreachable: ...`, no node can take it, or the container's own state). Ctrl+C only stops the waiting: emergency mode stays on.

```bash
sudo clouduler --config /etc/clouduler/cluster.yaml emergency --node atlas   # priority -1 stacks
sudo clouduler --config /etc/clouduler/cluster.yaml emergency site --node atlas
```

Mark the stacks you always want back first with `x-clouduler.priority: -1` (see the [stack spec](/docs/reference/stack-spec)). Within the emergency stacks, lower numbers start first.

`--node` defaults to the hostname (or `CLOUDULER_NODE`), `--yes` skips the confirmation. There is no dry run. `emergency` does not accept `--via`.

If the daemon is not managed by systemd the command cannot stop it, and fails with the database error `Database already open. Cannot acquire lock.`

## How it ends

Emergency mode clears **by itself** when the leader sees another **voting manager** reachable again (log: `another manager is reachable again, ending emergency mode`). Every stack then resumes from its own desired state; nothing needs restoring by hand. A worker coming back does not end it. A demoted manager does, once its daemon answers and it is re-added as a voter automatically. You cannot turn it off by hand.

The Nodes page shows the **No quorum** banner with "Emergency mode is on for the emergency stacks. It clears when the managers reconnect."

## Dangers

1. **Recent writes are lost.** The rescued node's copy of each volume is trusted as current. It may be behind the primary that died (replicas sync every 15 minutes by default), and whatever was never synced is gone.
2. **Old managers can conflict.** They are demoted, not deleted. If one returns with its old state intact it conflicts with the new log.
3. **It does not end if the lost manager never returns.** Removing the dead manager does not end it. Add a new voting manager (a manager join, see [Node lifecycle](/docs/features/node-lifecycle#add-a-node)). Two voters tolerate no failure, so add a third quickly.
4. **Other stacks are paused, not touched.** No other stack is scheduled anywhere until it ends: no new deploys, moves or restarts. Their desired state is untouched, and containers of other stacks that are already running on this node are left running as they are (not stopped, not removed, not recreated). Only the emergency stacks' own containers are acted on. Volume data is not deleted.
5. **`node remove` of the dead manager can fail.** It is refused while that node still owns instances, and emergency mode does not reschedule other stacks, so their instances stay assigned to it (the refusal reads `node X still runs INSTANCE`). The command's closing message suggests removing the lost manager, which can fail for this reason. Stop and remove those stacks first, or wait for a replacement manager.
6. Served drives the stacks use now point at this node, and every other node is marked unreachable until it answers.
