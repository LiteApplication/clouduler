# Stack spec

A stack is one YAML file that describes a group of containers (called services) for Clouduler to run across your cluster. This page lists every field the file accepts. It is a subset of Docker Swarm / Compose v3 plus an `x-clouduler` block for things Compose has no concept of: reverse-proxy routes, drive-backed volumes, node pins, actions and alert rules.

For the task-oriented view, see [Stacks](/docs/features/stacks). Terms like drive, overlay and placement are explained in the [glossary](/docs/intro/glossary).

Three rules to know before the tables:

- **Unknown keys are an error.** A typo fails the parse instead of being ignored, and `build:` is not supported.
- **Everything takes effect on redeploy.** The spec is stored as text. A change applies when you deploy a new revision, so the Reload column below reads `n/a` for every field.
- **Types.** `duration` is a humantime value (`30s`, `2m`, `1h30m`). `size` is a byte size (`10MB`, `64MiB`, `512M`, or a plain number of bytes).

## How validation works

Validation runs in two layers.

1. **Syntax** runs on every save in the web UI and on every deploy. It needs no cluster: names, shapes, port collisions, dependency cycles, and so on.
2. **Cluster checks** ask whether the network, drive and node you named actually exist and whether the service can be placed. The web UI, the HTTP API (and the MCP tools), the CLI (`clouduler stack deploy`) and the git-backup pull all run them, and refuse the deploy with a message when a drive, network or node pin does not exist.

Because the UI errors come back without a path, the message carries the whole location, for example `invalid config at services.web.env_file: ...`, and the editor does not highlight a line for it.

## A full example

This file touches most of the common fields. Comments explain each part.

```yaml title="gitlab.yaml"
version: "3.8"                         # ignored, optional

networks:
  wan: {}                              # a cluster network with a domain, used by the proxy route
  tailscale: {}                        # a second network, used by the SSH expose

secrets:
  db_password:
    file: ./secrets/db.txt             # read at deploy time, sealed with the cluster key
configs:
  gitlab_rb:
    file: ./conf/gitlab.rb             # bundled at deploy time

services:
  gitlab:
    image: gitlab/gitlab-ce:16.9.1-ce.0
    restart: unless-stopped            # the real restart policy lives here
    networks: [wan, tailscale]         # must be declared above
    environment:
      GITLAB_OMNIBUS_CONFIG: "external_url 'https://gitlab.example.com'"
    volumes:
      - fast/gitlab-data:/var/opt/gitlab    # drive/volume:/target
      - fast/gitlab-config:/etc/gitlab
      - bulk/gitlab-logs:/var/log/gitlab
      - type: tmpfs
        target: /tmp/cache
        tmpfs: { size: 64m }
    secrets:
      - source: db_password
        env: DB_PASSWORD               # exposed as an env var instead of a file
    configs:
      - source: gitlab_rb
        target: /etc/gitlab/gitlab.rb
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost/-/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 2m
    stop_grace_period: 2m
    deploy:
      replicas: 1
      resources:
        limits: { cpus: "2.0", memory: 4G }
    x-clouduler:
      node: atlas                      # hard pin, optional
      proxy:
        - host: gitlab                 # becomes gitlab.<domain of wan>
          network: wan
          port: 80
          tls: true
          middlewares: [redirect_https]
          max_body_size: 2GiB
          preserve_host: true
          response_timeout: 120s
      expose:
        - port: 22                     # container port
          published: 2222              # host port, bound on every node
          protocol: tcp
          network: tailscale
      backup:
        stop_before: true              # stop the service during a restic backup
```

### Stack names and service names

The stack name is not a spec key. It comes from the file name (CLI, without the extension) or the **Stack name** field in the web UI. It must be 1 to 63 bytes, start and end with a lowercase letter or digit, and use only `a-z`, `0-9`, `-` and `_`. The UI hint says "Lowercase letters, numbers and dashes", but the server also accepts underscores.

Each key under `services:` must be a DNS label (lowercase letters, digits and hyphens, not starting or ending with a hyphen, at most 63 characters). It is the service's hostname on the overlay and part of the container name `STACK_SERVICE_INDEX`.

<Quirk title="Fields that are parsed but currently not acted on" severity="info">
`deploy.restart_policy`, `deploy.update_config` and `deploy.resources.reservations.cpus` and `.memory` are validated but nothing in the scheduler or daemon reads them today. Use the service-level `restart:` for restart behaviour.
</Quirk>

<Quirk title="volume_sync enabled is rejected" severity="info">
`x-clouduler.volume_sync.VOL.enabled` used to be accepted and ignored. It is now an error naming the key, at stack and service level. Replication cannot be turned off per volume, because a failover starts an instance only on a node holding a current copy of every volume it mounts. Remove the key, give a rarely changing volume a longer `interval`, or keep scratch data on a drive that only one node implements.
</Quirk>

### GPUs

Two forms hand a GPU to a container.

NVIDIA GPUs use the compose device request:

```yaml
services:
  ml:
    image: ollama/ollama
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]
```

- `driver` is `nvidia` or left out (it means `nvidia`). Any other driver is a validation error.
- `count` is a number or `all`. `device_ids` lists GPU indexes or uuids instead. Setting both is an error. With neither, the request is for all GPUs.
- `capabilities` is required. Both `[gpu]` and `[[gpu], [compute]]` are accepted; the flat form is one set.

Intel and AMD GPUs (Jellyfin, Immich machine learning, Frigate) use the service-level `devices:` list, usually the whole DRI directory or one render node:

```yaml
services:
  jellyfin:
    image: jellyfin/jellyfin
    devices:
      - /dev/dri:/dev/dri
```

Each node detects its GPUs and reports them. A service is only placed on a node that has them: see [Placement](/docs/features/placement#gpus-and-devices).

## Common validation errors

The format is `invalid config at PATH: MESSAGE`, where PATH is a dotted path such as `services.web.volumes[0]`.

**Syntax errors (UI and CLI)**

- `service name must be a valid DNS label (lowercase letters, digits, hyphens, not starting or ending with a hyphen) since it becomes an overlay hostname`
- `env_file is not supported in a stack file; move its entries into environment, or paste it in the web UI's stack editor to import it`
- `network NET is not declared in this stack's top-level networks`
- `no service named DEP in this stack`, `a service cannot depend on itself`, `dependency cycle: a -> b -> a`
- `port P/PROTO is already published by services.X.ports[I]`
- `bind mounts are not supported, volumes must live on a drive so they can be replicated and migrated`
- `"SRC" must use drive/volume syntax, e.g. fast/gitlab-data`
- `mode: ingress is not supported, clouduler has no swarm-style ingress mesh; ...`
- `unknown restart policy "X", expected no, always, on-failure[:N] or unless-stopped`
- `"sigint" is not a signal name (e.g. SIGINT) or number`
- `must be greater than zero` or `must be at most 600s` (stop_grace_period)
- `write is not allowed on a secret, only on a config`
- `CFG is writable but this service runs N replicas; only one instance may write a config`
- `N is more than the maximum of 1000` (replicas)
- `expected KEY=value, got "ENTRY"` (list-form environment or labels)
- `mode: clouduler is read-only; set read_only: true`
- `x-clouduler.subnet` errors: `this stack has no overlay network`, `the prefix length must be between /8 and /29`, `has host bits set`, `overlaps the subnet ... of cluster network NET`
- ``allowed must be a list (write `allowed: []` to deny everything, or drop the key)``
- `invalid stack name "NAME": must be 1 to 63 bytes long`, `must start and end with a lowercase letter or digit`, `only lowercase letters, digits, - and _ are allowed`

**Cluster errors (CLI and git sync only)**

- `no network named NET declared in the cluster`
- `no node implements network NET, this service could never be placed`
- `only one egress network is allowed per service, found A and B` (a default-route container network counts)
- `SERVICE is the router of container network NET and is attached to it automatically, remove it from networks`
- `SERVICE is the router of container network NET and must run exactly one replica (no global mode, replicas at most 1)`
- `network NET is a container network, the router container decides what is reachable: remove its allowed list`
- `no drive named DRIVE declared in the cluster`
- `no node named NODE in the cluster`
- `network NET has no domain, so it cannot serve an HTTP route`
- `no node has P/PROTO open on network NET, this port could never be reached`
- `drive D can be served by more than one node (...), so mounting D/. (its whole root) is not allowed: pin a specific volume under it instead`

**Deploy errors (UI and API)**

- `config NAME needs content: it has no existing value to keep` (and the same for a secret)
- `this node holds no cluster key` (the node you are connected to cannot seal secrets)
- `stacks A and B would both use the overlay network ... which would break isolation between them: rename one of the stacks or networks`

**Deploy errors (CLI)**

- `this stack has secrets, so the cluster key at PATH is needed. Deploy from a node that holds it, or use the web ui`
- `NAME is N bytes, over the 1048576 byte limit` (each bundled config or secret file is capped at 1 MiB)

## Quirks and gotchas

<Quirk title="healthcheck without test is dropped">
A `healthcheck:` block with no `test:` is silently ignored. Other keys in it do nothing.
</Quirk>

<Quirk title="Bad cpus or memory values are ignored">
`cpus: "abc"` gives no CPU limit and no error. An unparseable `memory` gives no cap. Only a digit string too large for a 64-bit count is rejected.
</Quirk>

<Quirk title="deploy.mode: global ignores replicas">
You get one instance on every eligible node.
</Quirk>

<Quirk title="A stack-wide node pin is inherited">
`x-clouduler.node` at the stack level applies to every service that does not set its own. A whole-drive mount (`drive/.`) needs the pin to be the drive's sole holder, so adding a stack-wide pin can break a mount that worked before.
</Quirk>

<Quirk title="Redeploying an identical spec still bumps the revision">
The revision goes up by one on every deploy. The previous spec shown in "Changes since last deploy" stays at the last real change.
</Quirk>

<Quirk title="Redeploy keeps the name">
The name field is disabled when you redeploy. To rename a stack, deploy a new one and remove the old one. Removing a stack keeps its volumes.
</Quirk>

<Quirk title="Failed deploys can leave a stored spec">
The spec is stored first, then bundled files are written, and the object list is recorded last. If a step fails midway, retrying is safe.
</Quirk>

<Quirk title="An empty services map parses">
`services: {}` passes the syntax check, and no other validation step rejects it. The scheduler creates no instances for it, so it shows 0 instances and raises no problem.
</Quirk>
